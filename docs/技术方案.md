## 1. 系统概述与总体架构

## 2. 阶段一：法律文书知识库

### 2.1 数据模型设计

三张核心表 + 一张全文索引表：

**legal_document（文书主表）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | 文书唯一标识，如 `law_labor_contract_law` |
| name | TEXT | 文书全称 |
| doc_type | TEXT | 文书类型：`law`/`judicial_interpretation`/`administrative_regulation`/`rules`/`normative`，决定效力位阶 |
| issuing_authority | TEXT | 发布机关 |
| document_number | TEXT | 文号（含历次修正文号） |
| **status** | TEXT | 效力状态：`active`(现行有效)/`revised`(已修订)/`repealed`(已废止)/`draft`(草稿) |
| enacted_date | TEXT | 生效日期 |
| revision_date | TEXT | 最近修订日期 |
| repeal_date | TEXT | 废止日期 |
| source_url | TEXT | 官方发布来源（可追溯） |
| **verified** | INT | 是否经人工核验（0/1） |
| last_checked | TEXT | 最后核验时间 |

**document_version（版本表）**：一个文书可有多个历史版本，`status='active'` 的版本**有且仅有一个**，实现"版本管理"。

**legal_provision（条款表）**：条文级内容（`article_no` 如"第八十二条"、`content` 正文、`status` 条款级状态），**绑定所属版本**，支持条款级修订标记。

**legal_provision_fts（FTS5 全文索引）**：中文检索索引，入库时自动重建。

**效力状态机**（`versioning.py` 强制校验）：

```
draft ──发布──▶ active ──被新版本取代──▶ revised ──废止──▶ repealed
                  │                          │
                  └──────── 废止 ─────────────┘
                  repealed ──恢复(罕见，需人工核验)──▶ active
```

非法迁移（如已废止重复废止、active 文书存在多个 active 版本）一律拒绝并抛出明确错误。

### 2.2 知识库构建流程

```
官方来源采集(政府网/人大网) → 文本清洗 → 文书拆分(条款级) → 入库校验
→ 写入 DB + 重建 FTS 索引 → 人工核验标记(verify) → 纳入检索
```

1. **采集**：以官方发布源为准（中国政府网、全国人大网等，`source_url` 字段留存出处）；
2. **清洗**：去重、统一标点/编号、补全文号与修正记录；
3. **拆分**：按条款拆分，`article_seq` 保序；
4. **入库校验**（`validate_seed_document`）：必填字段、doc_type/status 枚举、条款编号唯一性、条款完整性；
5. **入库**：写文书 + 初始版本 + 全部条款，重建 FTS；
6. **人工核验**：`ingest verify <doc_id>` 标记 `verified=1` 并记录 `last_checked`——**未核验文书在正式上线时应禁止进入对外检索**（生产开关）。

### 2.3 入库与版本管理机制

命令行（`python -m app.ingest`）：

```bash
python -m app.ingest init                          # 初始化数据库
python -m app.ingest add data/seed/*.json          # 批量新增文书
python -m app.ingest update <doc_id> new.json --note "修订说明"   # 发布新版本
python -m app.ingest repeal <doc_id> --date 2026-06-01 --reason "被新法规取代"
python -m app.ingest verify <doc_id>               # 标记人工核验通过
python -m app.ingest validate                       # 全库时效/状态校验
python -m app.ingest list                           # 文书清单
```

**发布新版本（修订）事务逻辑**：
1. 校验文书存在且未废止；
2. 旧 `active` 版本 → `revised`；
3. 写入新版本（`active`）+ 新条款（替换旧条款，保证 `(document_id, article_no)` 唯一）；
4. 同步更新文书的 `revision_date` 等元数据；
5. 重建 FTS 索引。
全程单事务，失败自动回滚，保证一致性。

### 2.4 更新机制与时效校验

- **状态同步**：修订发布即生效——旧版条文自动不再参与检索，检索只命中 `status='active'` 的文书与条款（`active_only` 强制过滤），天然保证"检索优先返回现行有效文书"；
- **废止处理**：废止后文书、当前版本、条款三处状态同步为 `repealed`，记录废止日期，立即从检索结果消失；
- **全库校验（`validate_database`）**：定期巡检输出校验报告——
  - active 文书必须恰有一个 active 版本；
  - revised/repealed 文书不得残留 active 版本；
  - active 文书必须记录生效日期；
  - 列出全部"待人工核验"文书清单（正式上线前必须清零）；
- **更新来源**：生产环境接入定时任务（见 §7），按 `source_url` 比对官方发布页，检测到新修订即触发 `update` 流程并记录变更说明，保证"及时同步最新版本"。

## 3. 阶段二：法律咨询智能体

### 3.1 智能体架构与回答流程

```
用户问题 → 输入清洗 → 检索(active_only) → 范围判定(覆盖率+双字命中双信号)
   ├─ 范围外: 明确告知"知识库未收录"+ 引导 12348/12333（不臆造）
   └─ 范围内: 组装检索上下文 → LLM 生成（系统提示词强制约束）
              → 引用校验(引用即检索) → 出处标注 → 附加免责声明
```

核心约束（`agent.py` 中强制实施）：

1. **引用即检索**：系统提示词规定 LLM"只能引用检索结果中出现的条款"，并在后处理中用正则抽取回答中所有 `《文书》第X条` 引用，与检索结果集合比对，**未收录引用即告警并要求复核**——从机制上杜绝编造法条；
2. **范围外兜底**：范围判定采用**双信号**——实义字符覆盖率 ≥ 0.5，或覆盖率中等但查询与条文存在 ≥ 2 个连续双字命中（bigram）。双信号可防止"工/资/理"等常见字造成的宽泛误命中（如"火星移民的工资纠纷怎么处理"会被正确判为范围外）；判定为范围外时回答明确"该问题超出本知识库范围"，不猜测、不编造，引导用户拨打 **12348 法律援助热线 / 12333 人社服务热线**；
3. **免责声明**：所有回答统一附加"AI 辅助生成，不构成正式法律意见"。

### 3.2 检索方案

三段式：**召回 → 过滤 → 排序**

| 环节 | 实现 | 说明 |
|---|---|---|
| 召回 | FTS5 全文检索（BM25） | 中文"字符化"预处理（每字一 token），**短语匹配优先、单字 OR 宽召回兜底**（容忍"双倍工资"命中"二倍工资"等同义表述）；预留 `vector_channel` 向量通道扩展点 |
| 过滤 | `status='active'`（文书+条款） | 时效性强制约束 |
| 重排 | Python 端综合评分 | 实义字符覆盖率为主 + 效力位阶为辅（`coverage*100 + 位阶权重`），克服 BM25 在中文宽匹配下排序不可靠的问题 |

位阶权重（`config.DOC_TYPE_RANK`）：`law=5, judicial_interpretation=4, administrative_regulation=3, rules=2, normative=1`。同分时低位阶文档让位于高位阶文档，保证引用权威性优先。

**向量扩展（生产）**：在 `hybrid_rank` 处融合向量相似度（RRF 融合），可将检索升级为"BM25 + 语义双通道"，进一步提升口语化提问（如"老板跑路了"）的召回。

### 3.3 出处标注与可追溯

每条回答的 `citations` 数组携带完整出处元数据：

```json
{
  "document_name": "中华人民共和国劳动合同法",
  "article_no": "第三十条",
  "snippet": "用人单位应当按照劳动合同约定和国家规定，向劳动者及时足额支付劳动报酬……",
  "enacted_date": "2008-01-01",
  "revision_date": "2013-07-01",
  "status": "active",
  "score": 12.34
}
```

回答正文中的引用统一为"《文书名称》第X条"格式，前端可高亮展示"本条回答引用了哪些法律依据"，实现**文书名称、条款编号、生效/修订日期、效力状态**全维度可追溯。

### 3.4 防幻觉与可靠性兜底

- 机制防幻觉（引用即检索校验）> 提示词防幻觉，双层保障；
- LLM 调用失败（网络/Key 失效）时**安全降级**为"检索条文直出"，系统不报错、不空答；
- 绝对化措辞、编造法条在系统提示词与校验层双重拦截。

## 5. 核心代码实现

代码位于项目 `app/` 目录，模块职责：

| 文件 | 职责 | 关键函数 |
|---|---|---|
| `db.py` | 数据模型 DDL、连接、写入、FTS 重建 | `insert_document` / `_sync_fts` / `char_tokenize` |
| `versioning.py` | 版本状态机 | `publish_new_version` / `repeal_document` / `set_verified` |
| `validate.py` | 入库校验 + 全库校验 | `validate_seed_document` / `validate_database` |
| `ingest.py` | CLI 工具 | `add` / `update` / `repeal` / `verify` / `validate` / `list` |
| `retriever.py` | 检索 | `search` / `hybrid_rank` / `vector_channel` / `cite_of` |
| `llm.py` | LLM 客户端（降级） | `ChatClient.generate` |
| `agent.py` | 智能体编排 | `LegalAgent.answer` / `_verify_citations` / `_scope_check` |
| `main.py` | FastAPI 接口 | 见 §4 契约 |

**核心实现要点**：

1. **中文检索**（`db.char_tokenize` + `retriever._build_match_expr`）：FTS5 默认 tokenizer 不做中文分词，入库时将条文"字符化"（每字一 token），查询同样字符化后用短语匹配，以近似 n-gram 的方式支持中文子串召回，零分词依赖、可离线运行；
2. **版本一致性**：版本发布在同一事务内完成"旧版退役 → 新版写入 → 元数据更新 → 索引重建"，任一环节失败整体回滚；
3. **引用即检索**（`agent._verify_citations`）：正则抽取 `《…》第…条` 与检索命中集比对，越界引用自动告警；
4. **降级模式**：`ChatClient` 未配置 `LLM_API_KEY` 时 `generate()` 抛 `LLMUnavailable`，`LegalAgent` 捕获后直出检索条文，系统全程可用。

运行方式（见 README）：`pip install -r requirements.txt` → `python -m app.ingest init && add` → `uvicorn app.main:app --port 8000`。

## 6. 可靠性、可维护性设计

| 维度 | 措施 |
|---|---|
| 数据一致性 | SQLite 事务 + WAL；版本/废止操作原子化；非法状态迁移被状态机拦截 |
| 时效正确性 | 检索强制 `active_only` 过滤；全库校验报告定期巡检；废止立即生效 |
| 防幻觉 | 引用即检索校验（机制层）+ 系统提示词约束 + 范围外兜底 |
| 可用性 | 无 LLM Key 降级；LLM 调用异常安全降级不报错 |
| 可追溯 | 每条条文保留官方 `source_url`；引用携带生效/修订日期与效力状态 |
| 可维护 | 模块单一职责；CLI + API 双入口；种子数据与代码分离；配置集中在 `config.py` |
| 安全合规 | 免责声明强制附加；未核验文书禁止正式对外；个人信息处理遵循《个人信息保护法》（生产接入时） |

## 7. 生产化路线图

1. **数据同步自动化**：定时任务抓取官方发布页（按 `source_url`），比对修订信息自动触发 `update` 流程；
2. **向量检索升级**：接入 embedding 模型（sentence-transformers 或云端 API）+ Milvus，启用语义双通道 + RRF 融合；
3. **文书能力扩展**：接入司法文书模板库，智能体从"问答"扩展至"仲裁申请书/起诉状生成"（复用同一知识库与出处标注机制）；
4. **内容审核与限流**：接入内容安全审核、用户级限流与用量监控；
5. **多轮对话**：引入会话记忆，支持追问与上下文澄清。
